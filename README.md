## 1. Case study

**ECEWS SPEED Osun State Integrated HIV/TB Data Hub.** This is a public-health programme database for HIV and TB services in ~90 supported facilities across the 30 LGAs of Osun State.

- **Users:**
  - M&E officers and data clerks
  - Clinicians and case managers
  - Community outreach workers
  - Laboratory technicians
  - Programme coordinators
- **Major data:**
  - LGAs and facilities
  - Clients
  - HIV testing (facility and community outreach)
  - ART enrolment and multi-month drug pickups
  - TB screening
  - Viral load results
- **Key operations:**
  - Register and test clients
  - Enrol positives on ART
  - Record drug pickups
  - Flag missed appointments (interruption in treatment)
  - Screen for TB
  - Monitor viral suppression

All data in the repository is synthetic. It is generated by [seed_data.sql](portfolio-1-database-design/seed_data.sql): ~50,000 clients and ~650,000 rows, generated deterministically.

## 4. Portfolio summaries

**Portfolio 1: Design and Modelling.**

- Nine-table PostgreSQL schema in 3NF, with a Mermaid ER diagram and a normalisation walk-through from a flat facility register (UNF → 3NF).
- Integrity is enforced in the database through PK, FK, UNIQUE and CHECK constraints. Examples:
  - Viral-load status must match copies (≥1000 = unsuppressed).
  - TB treatment only for confirmed TB.
  - One pickup per client per day.
- Two denormalisations are deliberate and documented: the enrolment's current pickup snapshot and the VL status.

**Portfolio 2: Query Processing and Optimisation.**

- Four queries: IIT risk list, LGA TB/HIV co-infection cascade, latest unsuppressed viral load (window function), and the single-client chart.
- Measured with `EXPLAIN (ANALYZE, BUFFERS)` before and after indexing:
  - **IIT list:** 18.9 → 0.66 ms (Seq Scan → composite index scan, sort eliminated).
  - **Client VL history:** 2.5 → 0.04 ms (646 → 9 buffers).
- The aggregate cascade did not benefit from indexing.
- The window-function query traded a disk sort for random I/O with no net gain. An index that duplicated an existing UNIQUE index was rejected.

**Portfolio 3: Transactions and Concurrency.**

- Single-session scenarios show COMMIT, automatic rollback after a CHECK violation, explicit ROLLBACK, and SAVEPOINT partial rollback.
- A two-session script reproduced a **lost update** under READ COMMITTED: the final appointment was 2027-02-03 instead of 2027-05-04.
- The same script then showed three controls:
  - **`SELECT … FOR UPDATE`** blocks the second clerk and gives the correct result.
  - **REPEATABLE READ** raises a serialization error.
  - **The UNIQUE constraint** blocks a duplicate pickup entered from two workstations.

**Portfolio 4: NoSQL.**

- The relational data was migrated into one MongoDB document per ART client, with pickups, TB screenings and VL results embedded.
- The collection has a `$jsonSchema` validator, compound and multikey indexes (COLLSCAN → IXSCAN shown with `explain`), and an aggregation pipeline for suppression rate per LGA.
- Recording a pickup became one atomic single-document update; PostgreSQL needed a two-table transaction for the same operation.
- Unbounded array growth, duplication and cross-client analytics are discussed as trade-offs.

**Portfolio 5: Distributed and Cloud.**

- A Docker Compose primary + hot-standby replica with physical streaming replication and a replication slot.
- Evidence shows streaming status, a write visible on the replica within ~140 ms, rejected writes on the standby, and a failover by promotion.
- List partitioning by senatorial district demonstrated partition pruning, and it exposed skew (Osun Central = 42.9% of rows). This led to the decision to hash-shard on `client_id`.
- The cloud design specifies synchronous quorum replication (RPO = 0), PITR backups, encryption and NDPA 2023 data-residency review.

## 8. Technical reflection

I learnt a lot about databases and SQL while working on this. In my first draft, each pickup overwrote the dates on the enrolment row, which was simple, but it destroyed the information a retention programme exists to track, so I'd say I made a bad call with that design. You could not see how many pickups a client had made, couldn't tell which Multi-Month Dispensing (MMD) they were on, or when they first missed an appointment. The NoSQL model in Portfolio 4 had a full visit history while the relational model could not. That contradiction is what made me notice the problem. So by separating pickup history from the "current snapshot", and keeping that snapshot deliberately denormalised, ART_Pickups now stores every drug pickup (374,581 rows) and ART_Enrollments keeps a copy of only the latest last_pickup_date and next_appointment_date.

I also rejected the opposite extreme, which is the "textbook" fully normalised version with only the history table and no snapshot. With that, the missed-appointment list (Q1), which is the query the programme runs most, would have to work out each client's latest pickup from about 375,000 rows every single time. Keeping the snapshot and adding an index on (current_status, next_appointment_date) brought Q1 down from 18.9 ms to 0.66 ms, and the sort step disappeared because the index already returns rows in date order. I know a copy of data can drift away from the original, so I made sure the two tables are only ever updated together in one transaction. Scenario 2 in Portfolio 3 shows that if the second step fails, the first one is rolled back too. There's also a CHECK rule that the next appointment must come after the last pickup.

I'd also defend the enforcing of clinical rules in the database, and not just the application. chk_vl_status_consistent makes "Suppressed with 5,000 copies" impossible to store. I proved this in Scenario 4 of Portfolio 3. I rejected relying on the data-entry app to validate, because data arrives from many sources: facility EMRs, bulk uploads, and manual fixes. Only the database sees all of them.

I noticed a UNIQUE constraint was already doing the job of an index I planned to add. I expected the pickup-history lookup (Q4a) to need a new index on ART_Pickups(art_id, …). The "before" plan showed PostgreSQL was already using uq_pickup_per_day. That is the index behind my UNIQUE (art_id, pickup_date) rule, and its leading column is art_id. I tested the extra index, saw no improvement, and removed it because it would only have slowed down every pickup insert.

I was under the impression that in Postgres, declaring a foreign key would create an index. I learnt that it doesn't; only primary keys and UNIQUE constraints do.

That one fact explained most of the slow "before" plans. For example, opening one client's viral load history (Q4b) meant reading all 77,609 lab results just to return 4 of them. Once I indexed the client_id column, it went from 2.5 ms to 0.04 ms, and the pages read dropped from 646 to 9.

What surprised me most was Q3, the query that finds each client's latest viral load result. I added an index for it and PostgreSQL chose to use it, but the query didn't get any faster: it went from 46.4 ms to 49.3 ms. Before the index, PostgreSQL was sorting about 75,000 rows, and the sort was too big for memory, so it spilled 2.7 MB to disk. The index got rid of that sort, but because the query needs every row, reading through the index meant jumping around to a different page for almost every row. Pages read went up from 21,250 to 91,834. That's when it clicked for me that an index helps when you need a few rows, not all of them. A better fix for Q3 would be giving the sort more memory, or using a covering index so PostgreSQL can answer from the index alone.

Q2, the TB/HIV co-infection count per LGA, didn't improve at all either, but that one made sense. It adds up the whole state, so reading everything is genuinely the cheapest way, and PostgreSQL rightly ignored my index on lga_id. For a report like that, a summary table refreshed every night would make more sense than an index.

The lost update demo was the part that stayed with me. Two clerks edited the same client at the same time: one added 90 days for a 3-month supply and the other added 30 days for a top-up. The correct appointment date was 4 May 2027, but the database ended up at 3 February 2027. The 90 days just disappeared, and there was no error or warning; both clerks' saves "succeeded". I learnt that PostgreSQL's default setting (READ COMMITTED) doesn't protect against this. It happens when you read a value, think, and then save a new value based on what you read, which is exactly how a data-entry form works. In real life, that client would look overdue weeks early and a case manager could end up chasing someone who has three months of drugs at home.

Seeing the fixes run also showed me what each one costs. With SELECT … FOR UPDATE, the second clerk had to wait about 1.5 seconds for the first to finish, but the date came out right. That's why transactions have to be kept short. With REPEATABLE READ, the second clerk wasn't made to wait; their save was rejected with an error instead, so no data was lost, but the app would need code to retry. The UNIQUE rule stopped the same visit being entered twice no matter which setting was used. So I'd use locking for pickups, because conflicts on clinic days are likely and the edits are short, and the retry approach for overnight batch jobs. Concurrency control is something you have to decide on, not something the database handles for you by default.

If the programme grew to all 36 states, the data would go from hundreds of thousands of rows to tens of millions, and a few things would have to change. I'd add a States table above LGAs, because right now the state is just a text column that defaults to 'Osun'. The "OS-" client ID format would need to become a national ID, with a way to catch duplicates when someone moves state. I'd also add a transfers table, since moving between facilities would be much more common.

For splitting the data across servers, I wouldn't split by state. My partitioning test already showed how uneven geography is: Osogbo alone had 17.4% of Osun's clients, and Osun Central had 42.9% of the rows. Lagos would do the same thing nationally. I'd split by client ID instead, which spreads the load evenly and keeps each client's records together, and I'd keep small tables like facilities copied on every server. I'd also split pickups and lab results by year so older data can be archived.

Reports would run on separate copies of the database, so they never slow down the clinics. I'd use synchronous replication with two replicas and automatic failover, because losing a confirmed pickup matters more at that scale. Facilities with poor internet would need to capture data offline and sync it later, and the UNIQUE rules make that safe because a re-sent record gets rejected instead of duplicated. With many more clerks, I'd keep using locks but add a time limit so nobody waits forever. On security, each state's staff should only see their own state's clients, and the whole system would need a proper review under the Nigeria Data Protection Act 2023, because a national HIV register is a much bigger target than a single state's. For MongoDB, I'd split the collection by client ID too, and make sure every write is confirmed by most of the servers before it counts.
